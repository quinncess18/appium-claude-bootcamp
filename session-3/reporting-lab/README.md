# Reporting Lab — readable, shareable results 📊

> **Ready to run:** two login cases are implemented — **one passes** (valid login reaches home)
> and **one fails on purpose** (valid login, then a deliberately-wrong assertion) so the report
> shows a green *and* a red result, with a screenshot attached to the failure. Reporters +
> screenshot-on-failure hooks are wired. Just run it and open the report.

Live `spec` output is fine while you watch a run, but teams need **shareable reports** with
history, a clear pass/fail breakdown, and screenshots of what broke. This lab wires up exactly
that: **Node → Allure**, **Python → pytest-html**, each with a screenshot captured automatically
when a test fails.

## 0 · Prerequisites

- **Node** v20+ (for the WebdriverIO stack)
- **Python** 3.10+ (for the pytest stack)
- **Appium** 3.x with the UiAutomator2 driver, and **adb** on your PATH
- An Android emulator or device
- For Allure: the CLI ships as a devDependency (`allure-commandline`), so `npm install` brings it
  in — you only need **Java** installed and on your PATH (`java -version`).

## 2 · How it works

| | Node (Allure) | Python (pytest-html) |
|---|---|---|
| Reporter | `@wdio/allure-reporter` | `pytest-html` |
| Wiring | `reporters: ['spec', ['allure', { outputDir: 'allure-results' }]]` | `--html=report.html --self-contained-html` |
| Generate | `allure generate allure-results --clean` | produced inline by the run |
| Open | `allure open` (or `npm run report`) | open `report.html` in a browser |
| Screenshot on failure | `afterTest` hook → `browser.takeScreenshot()` | `pytest_runtest_makereport` → `driver.save_screenshot()` |

Both screenshot-on-failure hooks are already stubbed in the configs (`wdio.conf.js` /
`conftest.py`) — they only fire when a test actually fails.

## 3 · Start the emulator + Appium

```bash
# list AVDs, then boot one
emulator -list-avds
emulator -avd <your_avd> &

# in another terminal
appium
```

Confirm the device is visible: `adb devices`.

## 4 · What's in the suite

1. **Passing case** — a valid login that reaches the home screen (`~View All`) → green.
2. **Failing case** — a valid login (it *does* log in) followed by a **deliberately-wrong
   assertion** → red, with a screenshot of the home screen attached. This is intentional, to show
   what a failure looks like in the report.
3. Run the suite, then generate / open the report.
4. Confirm the **screenshot is attached** on the failing case (Node: inside the Allure step;
   Python: **embedded inline in `report.html`** via pytest-html extras, and also saved as
   `fail-*.png`). `report.css` (auto-applied via `pytest.ini`) renders that screenshot full-size
   instead of pytest-html's default thumbnail.

> Want to see the *other* kind of failure? Change the failing test to a wrong password and assert
> the home marker — it'll fail on login instead of the assertion.

## 5 · Run the lab

**Node**

```bash
cd node
npm install
npm test
npm run report     # allure generate + open
```

**Python**

```bash
cd python
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
pytest --html=report.html --self-contained-html
# then open report.html
```

## 6 · Make it yours

## 🆘 Troubleshooting

| Symptom | Fix |
|---|---|
| `allure: command not found` | Run `npm install` first — Allure ships as a devDependency (`allure-commandline`), and `npm run report` resolves it from `node_modules/.bin`. Also ensure **Java** is installed (`java -version`). |
| Empty / blank report | You ran from the wrong directory, or the `outputDir` doesn't match where results were written |
| No screenshot on failure | The hook only fires on a **real** failure — make sure the failing case actually fails |
| `ECONNREFUSED 127.0.0.1:4723` | Appium isn't running — start it with `appium` |
